# 0025 — Better Auth is the auth provider

Status:   accepted
Date:     2026-10-02
Deciders: kritpavin

## Context

Epic #9 needs sign-in, and Task #70 asks for the provider to be chosen and recorded before it is
built. The shortlist, the constraints and the rejected options are in the brain's
`auth-decision-brief.md`. Four constraints decide it:

- Identity is a generic subdomain: use an existing service, never our own (`domain-map.md`).
- Identity owns `Account` and `Profile` and nothing else. Workspace, Member, Role and Invitation
  stay in Thrive's own tables, and one Account may be a Member of several Workspaces.
- A personal Google account must be refused, which means reading the `hd` claim (#70).
- Google returns as an Integration in Epic #12. Its tokens must stay reachable so calendar scopes
  can be added later without a second sign-in.

ADR 0020 puts the database on Postgres, and ADR 0021 makes Prisma 7 the ORM.

## Decision

**Better Auth is the auth provider.** It runs as a library inside the NestJS API, and its tables
live in Thrive's Postgres. It reaches them through the Prisma adapter, on the one `PrismaClient`
the API already holds. It lives in `apps/api/src/infrastructure/auth/`, takes its secret and base
URL from the `AuthConfig` namespace (`BE_10`), and no module imports it directly. Its tables are
created by Prisma Migrate like every other table (ADR 0022).

## Alternatives

- **Clerk.** Fastest to a first sign-in, but Accounts live in Clerk, Google tokens are reached only
  through its API, and its Organizations feature duplicates the Workspace context. Rejected.
- **Supabase Auth.** Comes free with the database host, but Google tokens are reached through its
  API, and most of the platform would go unused because our own API owns the session. Rejected.
- **Auth0, Auth.js, Keycloak / Zitadel / Ory, WorkOS, building our own.** Rejected for the reasons
  in the brief.

## Consequences

- Google tokens sit in our own `account` table, so Epic #12 can add calendar scopes later.
- Refusing personal Google accounts by `hd` is our code to write and test, not a toggle.
- Session security and the auth secret are ours to own. `BETTER_AUTH_SECRET` is at least 32
  characters, is never defaulted, and comes from each environment's secret store (`INFRA_07`).
- **The organization plugin is not adopted.** Brief constraint 2 says it would hand the Workspace
  context to the library, so the auth schema was created without it. Adopting it later amends this
  ADR.
- On Supabase, the project's own `auth.users` exists beside Better Auth's `user` table. Better
  Auth's tables get their own schema there, and Supabase Auth stays unused.
- Better Auth's tables keep its own names: `user`, `session`, `account`, `verification`. Its
  `user` is a Thrive Account, and its `account` is one sign-in method. Renaming `user` to
  `account` was tried and fails: Better Auth resolves a model by its built-in names before any
  rename. These are the provider's tables; domain code never names them, so the glossary's ban on
  `User` holds above the infrastructure layer.
- Ids are UUIDv7 (`GEN_11`), generated by the application. The tables sit in `public` until
  Supabase is provisioned.
- The schema is generated, never hand-written: `bun run auth:generate` runs the CLI (pinned to the
  library's version) against `apps/api/scripts/auth-cli.config.ts`, because the app's instance is
  built by dependency injection. Prisma Migrate then applies it (ADR 0022). On a cold cache, the
  CLI adds `@better-auth/infra` to the root `package.json`; revert that before committing.
