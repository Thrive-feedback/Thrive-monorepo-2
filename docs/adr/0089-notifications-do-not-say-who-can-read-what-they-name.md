# 0089 — Notifications do not say who can read what they name

Status:   accepted
Date:     2026-11-14
Deciders: kritpavin

Supersedes design 0022 **D16** (a notification keeps its subject's audience and the bell draws it
as an icon) and the *"The line's audience is `EVERYONE`"* decision of
[ADR 0086](0086-a-kudos-tells-the-people-it-names.md). Everything else in 0086 stands.

## Context

D16 had every bell line end in the icon the feed cards use for a Visibility: Everyone, Selected
people, or Only the people it's for. To draw it, the notification copied its subject's Visibility
into a `notification.audience` column at write time, every event Feedback enqueues carried it, and
an Ask's Giver needed a rule of its own — told only when the answer goes on the Workspace feed —
because a Giver is not told who reads their answer (brain `ADR-0046` decision 4).

Seen in use, the icon does not help. A bell line is a pointer to something that happened to the
person; who else can read it is a property of the thing, and the thing says so where it is read —
on its card, which the line opens.

## Decision

**A bell line does not say who can read what it names.** The icon goes, and so does everything
that existed only to draw it: the `audience` column, the field on the list response, the
`audience` in each event's payload, the Feedback mapper that translated a Visibility into it, and
the Giver rule.

## Alternatives considered

- **Keep the data, remove only the icon.** Rejected: a column, a payload field and a special rule
  for Givers that nothing reads are cost with no use, and the data is a copy of Feedback's that would
  only be wrong if anybody started relying on it.
- **Drop the column in a later pull request, after the code that reads it is gone** (`BE_15` R10).
  Rejected by the owner in favour of one pull request; the cost is the deploy window below.

## Consequences

- **The migration is destructive and ships with the code that stops reading the column**, against
  `BE_15` R10 and `deploy.yml`'s rule that a migration must be readable by the code already running.
  `deploy.yml` migrates before it rolls the API, so until the new API is up the old one fails to list
  notifications, and its bell writes fail. The outbox does **not** ride that out: its five attempts
  back off 1, 2, 4 and 8 seconds on a 2-second poll, about 20–25 seconds in all, and an API rollout
  takes about as long, so an event raised in the window will most likely go dead — no bell line and
  no direct message, since the row is written before the message. After deploying, find them and
  replay them; a replay cannot send a message twice, because the row is written first:
  ```sql
  SELECT id, type, "lastError" FROM outbox_message
  WHERE type LIKE 'notifications.%'
    AND "deadAt" > (SELECT finished_at FROM _prisma_migrations
                    WHERE migration_name = '20261114153431_drop_notification_audience')
    AND "lastError" LIKE '%audience%';
  UPDATE outbox_message SET "deadAt" = NULL, attempts = 0, "availableAt" = now()
  WHERE id IN (<those ids>);
  ```
- **Rolling the API back is no longer safe on its own.** Every image older than this change selects
  and inserts `audience`, and `deploy.yml`'s rollback note points `thrive-api` at an older image
  without touching the schema. Before rolling back past this change, add the column back with a new
  migration — `ALTER TABLE "notification" ADD COLUMN "audience" TEXT;`, nullable, so the old code
  reads `NULL` as no icon. The dropped values are not restored. A `git revert` of this change is not
  a rollback: it deletes the migration's folder, but the database has already applied it, so the
  column stays gone and the reverted code fails the same way. The re-add is a new migration,
  generated by `migrate dev` like every other.
- **The audience data is lost.** Nothing reads it any more, and it was a copy of each subject's
  Visibility, which Feedback still holds.
- **The list response loses its `audience` field**, a breaking change (`GEN_08` R7), shipped with
  the web that stops reading it rather than after it (`GEN_08` R8). That is harmless here: the web
  live before this treats a missing audience as none and draws no icon, so an API deployed ahead of
  it changes nothing anybody sees.
- Old outbox messages that still carry `audience` drain as before: the payload schemas drop a key
  they do not know.
